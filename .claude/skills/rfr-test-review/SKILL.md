# Ревью тестов rfr-e2e: владение ресурсами

Ресурс — всё, что тест получает и обязан вернуть: строки БД, аренда пользователя из JVM-пула, `Page` или `BrowserContext`. Для каждого установи владельца, получение, хранение и освобождение.

## Правила

- **1. Владение данными `@User`.** Store хранит корневую `UserFixture` из `UserRequest.fixture()` и закрывает её как `AutoCloseable`. `Relation` задаёт список связанных пользователей, направление и статус; `UserWithRelationsFixture` владеет их фикстурами и связями.
- **2. Владение `@StaticUser`.** Store хранит `StaticUserFixture`; она арендует одну пару из общей потокобезопасной очереди и возвращает только её при `close()`. Этот путь не создаёт и не удаляет строки БД.
- **3. Регистрация до частичной подготовки.** Оба extension'а кладут фикстуру в Store до `create()`. Подготовка `@User` не атомарна, поэтому очистка должна выдерживать падение на любом шаге; отсутствующий API-профиль безопасно пропускается при удалении.
- **4. Симметрия `create()`/`close()`.** Для динамических данных удаляй собственные связи, затем связанные фикстуры и делегат в обратном порядке через `TearDown`. `ApiProfile.delete()` сначала удаляет строки `friendship`, находя идентификатор пользователя по username, затем удаляет профиль. Широких `DELETE`/`TRUNCATE` нет.
- **5. Новые предусловия.** Новый вид связи добавляй значением `Relation`, если его жизненный цикл совпадает с `UserWithRelationsFixture`. Для отдельного жизненного цикла добавляй новый `UserFixture`; не разветвляй `UserExtension`.
- **6. Параметры и Store.** Для `@User` и `@StaticUser` используется параметр `TestUser`; ключ Store включает индекс параметра. Связанные пользователи `@User` находятся в соответствующем списке `TestUser`, а статическая пара доступна только на время аренды.
- **7. Браузерные ресурсы принадлежат `@UsePlaywright`.** Не создавай и не закрывай `Page` или `BrowserContext` в тестах и extensions.
- **8. Слои.** В `jupiter` нет SQL и локаторов; в `data` нет JUnit; SQL находится только в `data/db`, и `db` не зависит от `data`. В `test` нет локаторов и SQL.
- **9. Подтверждай выводы.** `UserExtensionTest` проверяет создание/очистку динамических данных через `ValidUserTarget` и `FailingUserTarget`. `UsersQueueExtensionTest` проверяет четыре выдачи на пуле из трёх и возврат после падения; БД не использует. Сверяй имена мишеней с текущими пробами. При недоступной или небезопасной БД укажи проверку как «Не проверено». Не предлагай изменения без установленной причины.

## Формат

- Для каждого ресурса: владелец, получение, хранение, освобождение.
- Для каждого замечания: файл и строка, сценарий сбоя, способ воспроизвести (какая проба или какой падающий шаг `create()`).
- Три списка: «подтверждено запуском», «по чтению кода», «не проверено».
- Если дефектов нет, так и скажи и перечисли ограничения решения.
