# Unit Tests

## Область применения

- Применяй этот skill к быстрым unit-тестам. Для `EngineTestKit`, HTTP-проб, реальной MySQL, HikariCP и JUnit Extensions дополнительно применяй `rfr-test-review` и `rfr-e2e/AGENTS.md`.
- Соблюдай глобальные правила `Testing`, `Code`, `Objects` и ограничения запуска. Специализированный skill не отменяет запреты на операции с Git и неподтверждённые внешние действия.

## Разработка

- Для воспроизводимого дефекта по возможности сначала запиши падающий тест, затем исправь код и повторно запусти его (red-green-refactor). Не утверждай, что тест был красным или зелёным, если не выполнял его.
- Один тест — одно значимое поведение с преимущественно одним основным Act. Несколько `assert` допустимы, если совместно подтверждают один наблюдаемый результат, в том числе жизненный цикл ресурсов.
- Используй понятные имена тестов по соглашениям модуля; для JUnit по необходимости добавляй `@DisplayName`.
- Тестируй публичный контракт, а не приватные методы или случайную последовательность внутренних вызовов. Наблюдаемые побочные эффекты — записи в БД, файлы, HTTP-ответы и закрытие ресурсов — могут быть предметом проверки.
- Не добавляй тесты тривиальных геттеров и конструкторов без реального контракта. Не создавай публичные методы исключительно ради доступа теста к приватной реализации.
- Для вариантов входных данных используй параметризованные тесты, если это делает различия очевиднее. Применяй воспроизводимые значения и детерминированные проверки.

## Изоляция и фикстуры

- Каждый тест независим от порядка запуска, выполняется отдельно и не полагается на изменяемое состояние других тестов.
- Для простой независимой подготовки/очистки допустимы `@BeforeEach` и `@AfterEach`; для повторно используемых жизненных циклов, параметров и общих ресурсов предпочитай JUnit Extensions и `ExtensionContext.Store`. Не создавай extension ради тривиального присваивания.
- Предпочитай настоящие объекты и управляемые фейки избыточным мокам. Не мокай память или файловую систему, когда можно использовать реальные изолированные ресурсы.
- Для файлов используй `@TempDir`, для локального HTTP — эфемерные порты. Освобождай только принадлежащие тесту ресурсы.
- Для ожиданий используй условие или синхронизацию с конечным таймаутом. Не добавляй произвольные `Thread.sleep` или повторные прогоны для маскировки нестабильности.
- Для unit-теста не запускай полноценный Spring context без необходимости. `@SpringBootTest` применим к соответствующему интеграционному тесту; `MockitoExtension` нужен только при использовании Mockito.

## Проверка результата

- Проверяй наблюдаемое состояние, возврат, файл, ответ API или документированный эффект. Для структурированных артефактов проверяй содержимое, а не только факт создания.
- Проверяй ошибки и очистку, когда они относятся к контракту. Не ослабляй assertions и не отключай тест ради успешного результата.
- Запускай тесты только после разрешения пользователя, если текущий запрос не дал его явно. Отделяй подтверждённое выполнением от выводов по чтению кода.
