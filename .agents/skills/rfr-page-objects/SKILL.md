# Page Objects Rangiffler

Страницы — `rfr-e2e/src/test/java/io/student/rangiffler/ui/page`, общие части — `ui/component`, адреса — `config/TestConfig`.
Доступные имена и роли элементов подтверждай в браузере через Playwright MCP по адресам из актуальной конфигурации `TestConfig`, не угадывай по исходникам фронта.

## Контракт

1. Класс `final`, поля `private final`: `Page`, `Locator`, компоненты. Исключение — `public static final String URL` с базой из `TestConfig`; он есть у каждой страницы, даже если на неё попадают только переходом.
2. Конструктор страницы принимает только `Page`. Компонент получает `Page`, если ему нужно создавать локаторы от страницы. **Исключение:** если дочерний компонент работает только внутри элемента, передавай ему ограниченный этим элементом `Locator` в конструкторе или в методе. При передаче в метод компоненту не нужны поле `Page` и конструктор с параметрами. Конструкторы только присваивают поля, без переходов, кликов, проверок, ожиданий и SQL.
3. Композиция вместо наследования: общие части оформляй компонентами, базовых классов нет. Родитель выбирает область дочернего компонента, а дочерний компонент инкапсулирует работу внутри неё.
4. Каждый публичный метод страницы и компонента — с `@Step`. В название шага включай только необходимые несекретные параметры, например `@Step("Заполнить форму входа для {username}")`. Пароли, токены и другие секреты не должны попадать ни в текст шага, ни в отображаемые параметры Allure; проверь их скрытие средствами используемой версии Allure. Одного исключения `{password}` из шаблона может быть недостаточно, если Allure автоматически записывает параметры метода.
5. Переход возвращает объект следующей страницы, действие и проверка на текущей — `this`.
6. Одно бизнес-действие — один метод, имя которого называет форму: `fillLoginForm(username, password)`, `fillRegistrationForm(...)`. Без безликих `fillForm`/`fill`/`submit` и цепочек `fillUsername().fillPassword()`; отдельный метод на поле — только если тесту нужно именно поле (валидация).
7. В UI-тестах, Page Objects и UI-компонентах разрешены только web-first assertions Playwright через `PlaywrightAssertions.assertThat(...)`. Любые другие ассерты запрещены, включая JUnit, AssertJ, Hamcrest и Java `assert`. Не заменяй web-first assertions ручными проверками через `if`, `locator.isVisible()` или `locator.count()`. Действия `fill…`/`click…` ничего не проверяют, а методы `checkThat…` выполняют только проверки.
8. Без `checkThatOpened`, `checkPageLoaded`, `isLoaded`, `waitUntilLoaded`: `click`/`fill` ждут элемент, web-first assertions ждут состояние. URL и видимость страницы проверяем, только когда переход и есть предмет теста.
9. Локаторы: `getByRole` с точным `name`, `getByLabel`, `getByPlaceholder`, `getByText` с точным совпадением, `getByTestId`. Без `first()`/`nth()`, MUI-классов и XPath; неуникальный элемент сужай родителем: `page.getByRole(AriaRole.BANNER).getByRole(…)`.
10. При действиях, вызывающих мутации данных, используй `page.waitForResponse(predicate, action)`: ожидание ответа должно регистрироваться до запуска действия, вызывающего запрос, и завершаться до следующего действия.
11. Для MUI `Select` открывай `COMBOBOX` и выбирай `OPTION`, отфильтрованный по `IMG` с точным именем.
12. Проверка не должна быть тавтологией локатора: `assertThat(heading("Travels map")).hasText("Travels map")` ничего не доказывает. Ожидаемое значение приходит из теста (`checkThatUsername(username)`).
13. Вход только через UI; `access_token`/`id_token` в `localStorage` не подставлять (до занятия 13).
14. Для каждого нового класса добавляй один краткий docblock о его назначении, как требует глобальное правило `Code`. Не добавляй комментарии и Javadoc к отдельным методам без необходимости объяснить неочевидный контракт: смысл передают имена методов и текст `@Step`.

### Пример: `PeopleTable` → `PeopleRow`

`PeopleTable` уже хранит `Page`, поэтому сам находит строку среди строк таблицы по точному имени пользователя и передаёт её локатор в `PeopleRow`. `PeopleRow` ищет кнопки только внутри этой строки и может оставаться без полей.

```java
// PeopleTable
private Locator matching(String username) {
  return rows().filter(new Locator.FilterOptions().setHas(
      page.getByRole(AriaRole.CELL, new Page.GetByRoleOptions().setName(username).setExact(true))
  ));
}

// PeopleRow
void checkInvitationSent(Locator row) {
  PlaywrightAssertions.assertThat(row.getByRole(AriaRole.BUTTON,
      new Locator.GetByRoleOptions().setName("Cancel").setExact(true)
  )).hasCount(1);
}
```

Вызов из `PeopleTable`: `row.checkInvitationSent(matching(username))`.

## Проверка результата

При наличии разрешения на запуск подтверждай сценарий тестом: для UI используй `./gradlew e2e --tests '<Тест>'`, для тестов без UI — `./gradlew :rfr-e2e:test --tests '<Тест>'`. Проход сценария через MCP запуском теста не считается.
В отчёте разделяй: что подтверждено браузером через MCP, что подтверждено Gradle-запуском, а что установлено только по исходникам. Если запуск не разрешён, укажи «Не проверено».

### Правила написания тестовых классов

- **Запрещено** оборачивать всё тело тестового метода в `Allure.step("Название сценария", () -> { ... })`.
- **Почему:** Тестовый метод сам по себе является сценарием. Оборачивание создает лишний уровень вложенности в отчете и дублирует название теста.
- **Как надо:** Пиши вызовы Page Objects в виде одной непрерывной цепочки (Fluent Interface) прямо в теле метода `@Test`.
- **Аннотации:** Для названия теста используй `@DisplayName` из JUnit Jupiter 6, а для описания в Allure — `@Description`, `@Feature` или `@Story`.

## Из практики ДЗ 5: карточки и списки

16. Повторяющийся элемент (строку, карточку) оформляй компонентом в `ui/component`. Найди набор элементов по роли или test-id и сузь его по уникальному тексту с точным совпадением. Позиция в списке может измениться.
17. Ищи кнопки повторяющегося элемента внутри локатора компонента. Поиск от страницы может совпасть с кнопками нескольких элементов и дать `strict mode violation`.
18. Размер списка проверяй через `assertThat(list).hasCount(n)`. Эта проверка дожидается нужного числа элементов, а `count()` возвращает текущее значение сразу.
19. Если по ширине меняется разметка, ставь один и тот же test-id на оба варианта элемента и уточняй его по тексту. Роли `row` и `cell` могут исчезнуть в мобильной раскладке. Проверяй сценарий также на 390×844.
20. Если доступное имя элемента меняется, ищи его по имени в том состоянии, в котором выполняешь действие. Пункт всплывающего списка ищи внутри контейнера с его фактической ролью.
